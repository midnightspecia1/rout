# rout — план реализации

Нативное Windows-приложение в духе Nyxt hint-mode / Homerow: по хоткею
показывает поверх всего экрана метки на кликабельных объектах активного
приложения и позволяет "кликнуть" клавиатурой, без мыши.

Целевые приложения на старте: браузер (Chrome/Edge), VS Code, Rider,
Claude Desktop. Остальные приложения — через общий fallback.

## Архитектура

- **Core Engine (C++)** — единственный владелец оверлея и глобального
  хоткея. Рисует метки, перехватывает ввод при открытом оверлее,
  выполняет клик сам только в generic-пути (через UI Automation).
- **Адаптеры** — лёгкие клиенты, подключаются к Core по локальному
  WebSocket (127.0.0.1, фиксированный порт, авторизация токеном из
  файла с ограниченным ACL). Если адаптер способен выполнить действие
  сам (DOM `element.click()`, `commands.executeCommand`, вызов
  IntelliJ-экшена) — делает это сам, а не просит Core кликать по
  координатам. Это снимает проблемы DPI/мультимонитор/фокуса для
  "умных" адаптеров.
- **Protocol v1** (JSON по WS):
  - Core → адаптер: `{"cmd":"get_hints"}`, `{"cmd":"activate","id":"..."}`
  - Адаптер → Core: `{"type":"hello","app":"...","pid":...}`,
    `{"type":"hints","items":[{"id":"...","rect":[x,y,w,h]}]}`,
    `{"type":"ack"}`
- Core хранит таблицу `имя процесса → адаптер`. По хоткею определяется
  foreground-процесс (`GetForegroundWindow` → `GetWindowThreadProcessId`
  → имя exe); если для него есть живой адаптер — запрос идёт туда,
  иначе — generic UI Automation путь.

## Модули и порядок выполнения

### M0 — скелет Core
- Глобальный хоткей (`WH_KEYBOARD_LL`), без отдельного потока —
  message loop уже есть в `WinMain`.
- Layered/topmost/click-through/no-activate overlay-окно на весь
  virtual screen (все мониторы).
- Рисование статичных демо-хинтов (заглушка вместо реальных
  данных от адаптеров/UIA).
- Esc закрывает оверлей без действия.
- Рендер — обычный GDI с `LWA_COLORKEY` (бинарная прозрачность, без
  альфа-блендинга) — достаточно для проверки механики hook/overlay/
  click-through/DPI. Полупрозрачность и анти-алиасинг — отдельная
  задача позже (см. M6/темизация).

### M1 — generic UI Automation fallback
- `IUIAutomation`, обход foreground-окна с условием на
  `InvokePattern`/`TogglePattern`/`SelectionItemPattern`/
  `ExpandCollapsePattern` либо нужный `ControlType`.
- Лимит глубины/таймаут обхода (деревья Chromium/Electron большие).
- `BoundingRectangle` → экранные координаты хинта.
- Клик — `SendInput` по центру rect, т.к. адаптера нет.
- Проверка на Claude Desktop и паре обычных приложений (Notepad,
  Explorer).

### M1b — поиск по имени элемента (в духе Homerow)
- Причина: даже после фильтрации шума (классификация по
  `ControlType`, отсечение перекрытых/disabled/off-screen) на
  тяжёлых страницах остаётся ~100+ хинтов — двухбуквенные метки,
  глазами искать долго.
- Отдельный режим (свой хоткей или префикс-клавиша в оверлее):
  пользователь печатает часть имени — остаются только элементы, чей
  `Name` (UIA) содержит введённое, без учёта регистра.
- Сборщик кэширует `UIA_NamePropertyId` и отдаёт его вместе с rect.
- Метки перераздаются по отфильтрованному набору, так что при
  ≤26 совпадениях метки снова однобуквенные; Enter при единственном
  совпадении — сразу клик.
- Элементы без имени в этом режиме не показываются.
- В адаптерах (M3/M4) имя берётся из их источника (текст/`aria-label`
  в DOM, текст экшена в IntelliJ), протокол `hints` получает
  опциональное поле `name`.

### M1c — режим прокрутки (в духе Emacs)
Идея: выбрать прокручиваемую область (чат, список в Explorer, страница)
и крутить её с клавиатуры, не трогая мышь.

**Поиск областей.** Сборщик дополнительно отдаёт элементы с
`ScrollPattern`, у которых `VerticallyScrollable`/
`HorizontallyScrollable` = true. Это отдельный вид хинта: рисуется
иначе (рамка по контуру области + метка в углу), чтобы не путать с
кликабельными.

**Вход.** Действие определяется тем, что выбрано меткой, а не
правилом по умолчанию:
- метка прокручиваемой области (страница, лента сообщений, список) —
  режим прокрутки этой области;
- метка поля ввода (поле чата, адресная строка, поиск) — фокус и
  каретка в поле, можно сразу печатать (как обычный клик по edit);
- остальное — обычный клик.

У вложенных областей (лента чата внутри прокручиваемой страницы) —
свои метки у каждой, так что выбор однозначен.

Отдельный хоткей «сразу прокрутка» (без выбора): берёт ближайшую
прокручиваемую область-предка элемента, на котором сейчас фокус
(`GetFocusedElement` + подъём по дереву); если фокуса внутри
прокручиваемой области нет, а область в окне одна — её.

**Клавиши (предлагаемое).**
- `Ctrl+N` / `Ctrl+P` — строка вниз/вверх (автоповтор при удержании
  работает сам — это повторные keydown).
- `Ctrl+V` / `Alt+V` — страница вниз/вверх.
- `Alt+<` / `Alt+>` — в начало/конец.
- `Ctrl+F` / `Ctrl+B` — горизонтально, если область это умеет.
- Только с модификаторами: голые `n`/`p`/`j`/`k` не используются,
  потому что любая клавиша вне таблицы выходит из режима и уходит в
  приложение (см. «Выход») — печатные символы должны оставаться
  печатными.

**Как крутить.**
1. `IUIAutomationScrollPattern::Scroll(SmallIncrement/LargeIncrement)`
   и `SetScrollPercent` для начала/конца — без движения курсора;
   работает для нативных списков (Explorer) и, как правило, Chromium.
2. Fallback, если паттерн отказал: колесо через `SendInput` над
   центром области (курсор временно переносится туда и
   возвращается). Наш собственный ввод помечен `LLMHF_INJECTED` и не
   сбрасывает режим.

**Выход.**
- `Esc`, `Ctrl+G` (как в Emacs), повторный хоткей.
- Любое действие мышью — то же правило, что для хинтов.
- Смена foreground-окна (`SetWinEventHook(EVENT_SYSTEM_FOREGROUND)`)
  — например, Alt+Tab или всплывшее уведомление.
- Область исчезла / `Scroll` вернул `UIA_E_ELEMENTNOTAVAILABLE`.
- Любая другая клавиша (включая сочетания с модификаторами) — выход
  **с пропуском клавиши в приложение** (как isearch в Emacs): можно
  сразу начать печатать. Голые модификаторы (нажатие самого Ctrl/
  Alt/Shift) режим не сбрасывают — иначе не набрать `Ctrl+N`.
- Таймаут бездействия: 10 с без клавиш прокрутки — выход. Значение
  потом выносится в настройки (M6).

**Индикация.** Пока режим активен, вокруг области — тонкая рамка и
бейдж «SCROLL»: клавиатура перехвачена, без индикатора это выглядит
как «сломалась клавиатура».

**Связка с хинтами.** Из режима прокрутки клавиша (например, `f`)
показывает хинты только внутри текущей области — заодно решает
проблему «слишком много хинтов».

**Статус.** Сделано: сбор областей (ScrollPattern; документ без
паттерна — через колесо), вход по метке, клавиши, все условия выхода,
рамка и бейдж. Отличие от черновика: в режиме хинтов области
отмечены только оранжевой меткой в правом верхнем углу, без рамки
(рамки всех областей сразу — шум); рамка рисуется у активной.
Не сделано: хоткей «сразу прокрутка» (нужно выбрать сочетание),
`f` — хинты внутри области (конфликтует с правилом «любая клавиша
выходит», нужна другая клавиша).

**Открытые вопросы.**
- Область не поддерживает `ScrollPattern` и колесо её тоже не крутит
  (canvas, кастомный рендер) — молча выходить или показать отказ?
- Elevated-окна (админские): UIPI блокирует и UIA, и `SendInput` —
  режим недоступен, нужно хотя бы не зависать в нём.

### M2 — IPC-сервер в Core
- Локальный WebSocket-сервер (готовая header-only библиотека, не
  писать RFC6455 руками), токен-авторизация.
- Реестр подключений по полю `app` из `hello`.
- Таймаут ожидания `hints` от адаптера (150–250 мс), иначе —
  fallback на generic UIA даже для "умной" цели.

### M3 — браузерный адаптер (расширение MV3)
- Background service worker держит WS-клиент к Core.
- Content script собирает `a`, `button`, `[role=button]`, `input`,
  `[onclick]`, элементы с `tabindex`, с проверкой видимости.
- Перевод координат через `window.screenX/screenY` + поправка на
  высоту UI браузера.
- `activate` — `element.click()`/`element.focus()` в content script,
  без синтетического OS-клика.

### M4 — Rider adapter (плагин IntelliJ Platform, Kotlin)
- `ProjectActivity` поднимает WS-клиент при старте проекта.
- `get_hints` собирает: intention actions в текущей позиции курсора,
  gutter-иконки (`LineMarkerProvider`), breadcrumbs, таб-бар, кнопки
  тулбара — через их Swing-компоненты (`getLocationOnScreen`) и
  `editor.logicalPositionToXY`.
- `activate` — программный вызов `IntentionAction`/`AnAction`, а не
  симуляция клика.

### Проверка Claude Desktop
- Отдельного адаптера нет — чисто generic UIA (M1/M2). Прогнать и
  явно зафиксировать, каких элементов не хватает.

### M5 — эксперимент с VS Code (риск, не гарантирован)
- Extension host не имеет прямого доступа к DOM/пикселям своего UI
  (в отличие от content script на обычной странице и Swing-компонента
  в Rider). Варианты: подключение через Chrome DevTools Protocol
  (`--remote-debugging-port`) или грубая оценка координат через
  метрики строк/`visibleRanges`. Решение go/no-go по итогам
  эксперимента; до этого — VS Code покрывается только generic UIA.

### M6 — Settings window + пресеты тем
- Tray-иконка (`Shell_NotifyIcon`) с меню "Settings…" / "Reload
  adapters" / "Exit".
- Native Win32-диалог: выбор пресета (Dark/Light/Minimal/High
  Contrast/Nyxt-yellow) + несколько override-слайдеров (акцент,
  прозрачность, размер шрифта, радиус скругления) + preview-панель,
  рисующая тот же код, что и реальный оверлей.
- Пресеты — таблица `Theme`-структур в коде, не произвольный
  стайлинг (CSS/WebView2-вариант рассмотрен и отклонён — слишком
  тяжело для той ценности, которую даёт).
- Функция отрисовки хинта параметризована `Theme` с самого M0, чтобы
  не переписывать рендер заново на этом шаге.
- Сохранение выбора в `%APPDATA%\rout\settings.json`.
